# Claude Code Variant — ファイル操作による構成生成

Claude Codeで本スキルが起動した場合の振る舞いを規定する。

## 基本姿勢

Claude Codeでは、Hiromiさんはファイル単位で作業を委ねている。
対話の往復を減らし、判断を Claude Code 側に委譲しつつ、ファイル操作の正確性を担保する。

## ユースケース別フロー

### ケースA: 新規ドキュメントの生成

```
ユーザー指示例:
「来週のFellows VISワークショップの台本を作って。
テーマは『ブランドの意味の余白』。
出力先は ./workshops/2026-05-22-fellows/ に。」
```

#### フロー

1. **コンテキスト読み込み**:
   - プロジェクトルートの `CLAUDE.md` を読む
   - 関連する過去のWS台本があれば参照する（`./workshops/` 以下を探索）
   - Hiromiさんのスタイルガイドや `soul.md` があれば参照する

2. **構成案の提示（最小限）**:
   - 立ち上げたい結論、配置する点、順序、穴の候補を箇条書きで提示
   - 承認を求める（ただし詳細な対話はしない）

3. **ファイル生成**:
   - 適切なテンプレートを使って台本を生成
   - 指定されたパスに保存
   - メタ情報、点の配置、演技指示、想定Q&Aをすべて埋める

4. **関連ファイルの生成（必要に応じて）**:
   - スライドのアウトライン（別ファイル）
   - 配布資料（別ファイル）
   - これらのファイル間で参照が一貫しているか確認

5. **コミット**:
   - 関連ファイルをまとめて意味のある粒度でコミット
   - コミットメッセージは「workshop: add Fellows VIS script (2026-05-22)」のような形式

### ケースB: 既存ドキュメントのリファクタ

```
ユーザー指示例:
「./drafts/explainer.md を点と線型にリファクタして」
```

#### フロー

1. **既存ファイルの読み込みと構造分析**:
   - 現状の構成（結論先出し型か、すでに発見駆動型か）を判定
   - 結論先出し型なら、結論を1文で抽出
   - 点として使えそうな段落を抽出

2. **リファクタ計画の提示**:
   ```markdown
   現状の構成を分析しました：

   - 検出された結論: ○○
   - 抽出した点（3つ）: [...]
   - 提案する順序: [...]

   この方針でリファクタしますか? 元ファイルは ./drafts/explainer.md.bak にバックアップします。
   ```

3. **バックアップ作成**:
   - 元ファイルを `.bak` 拡張子でコピー
   - これは必ず行う。発見駆動型リファクタは情報を「減らす」方向の編集なので、元に戻したくなる可能性が高い

4. **リファクタ実行**:
   - 適切なテンプレートに沿って再構成
   - 元の文章の表現や事例はできるだけ保持する（書き直しではなく再配置）

5. **差分の提示**:
   - 何を移動したか、何を削ったか、何を追加したかを明示
   - Hiromiさんが意図と合うか判断できる粒度で

### ケースC: 複数ドキュメント間の整合性管理

```
ユーザー指示例:
「./course/ 配下の全チュートリアルを点と線型に統一して」
```

#### フロー

1. **対象ファイルの一覧化**:
   - 対象となる全ファイルを列挙
   - 各ファイルの現状の構成タイプを判定

2. **共通の設計原則の提案**:
   - シリーズ全体で「発見してほしい原理」が積み上がっていく構造を設計
   - 各チュートリアルがシリーズ内のどの位置で何を発見させるかを設計

3. **個別ファイルへの反映**:
   - ケースBの手順を各ファイルに適用
   - ただし、ファイル間の参照（「前回のチュートリアルで触れた○○」など）の整合性を保つ

4. **シリーズ全体のメタファイル更新**:
   - `README.md` や `index.md` があれば、シリーズの全体像を発見駆動型で再構成

## CLAUDE.md との連携

プロジェクトルートに `CLAUDE.md` があれば、以下のような連携を行う：

- プロジェクト固有の用語・概念があれば、それを使う
- 禁止ルール（F1-F5など）があれば遵守する
- Hiromiさんの普段の文体指針があれば優先する

本スキルの中核原理（点と線・さそいこみ・予定実行結果サイクル）は、`CLAUDE.md` の指示と矛盾しない限り適用する。
矛盾した場合は `CLAUDE.md` を優先する。

## ファイル命名規則

- ワークショップ台本: `workshop-YYYY-MM-DD-[topic].md`
- プレゼン台本: `presentation-YYYY-MM-DD-[event].md`
- 解説記事: `[slug].md` または `YYYY-MM-DD-[slug].md`
- チュートリアル: `tutorial-[number]-[topic].md`

ただし、プロジェクト側に既存の命名規則があればそちらを優先する。

## 出力後のセルフチェック

生成・編集後、必ず以下を実行：

1. `SKILL.md` のアンチパターン表に照らして自己チェック
2. 「何を言う/書く」と「何を言わない/書かない」の両方が埋まっているか確認
3. 意図的な穴が最低1つ設計されているか確認
4. 演技指示（WS・プレゼン台本の場合）または余韻設計（記事の場合）が含まれているか確認

問題があれば、即座に修正版で上書きする。

## コミットメッセージのテンプレート

```
[type]: [short description]

- 構成: 点と線型（発見駆動）
- 配置した点の数: N
- 意図的な穴: あり / なし
- リファクタ元: [元ファイル名（リファクタの場合）]
```

type は `workshop`, `presentation`, `article`, `tutorial`, `refactor` のいずれか。
